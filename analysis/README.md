# 市政 debug 松：議題分析模擬

> 本專案由一位個人參加者用 AI 協助製作，與主辦單位無關。`[AI模擬]` 的內容不是真實訪談，也不是真實市民的話；`[AI整理]` 的內容由 AI 從真實資料整理，還沒有經過真人查核；`[實證]` 的內容有可查證的出處，或已經由真人查核；`【待補：…】` 需要真人提供。

整個專案的說明（網站、資料再利用、授權）見[根目錄的 README](../README.md)。

## 這是什麼

一位市政 debug 松的報名者，在 AI 輔助模擬下，將個人在商業界常用的需求分析方法，套用到黑客松的議題，希望能幫助所有參與者一起產出品質更好的市政提案。

## 為什麼要做這個

黑客松的時間很短，參加者容易直接從題目裡的資料和舉例開始動手。這份模擬想補上一個步驟：在動手做之前，先看見利害關係人的多樣與衝突。這樣做出來的提案，比較容易說明「為什麼」，也比較能接住 100 天內落地的目標。

## 議題分析模擬採用的 7 個步驟

| 步驟 | 名稱 | 內容 |
|---|---|---|
| 1 | 利害關係人與輸入來源 | 列出利害關係人，分成**組織**（產業、政府、學術、非營利）與**個人**（居民、高齡者、身心障礙者、外籍居民等），並列出每一方可能的意見來源 |
| 2 | 初始使用者故事 | 用「身為…，我想要…，以便…」寫下使用者故事：「我想要…」是他心中的解法（想要），「以便…」是他得到的好處（需要）。題目原文的內容，放在它最可能代表的利害關係人之下。想要與需要放錯格子時，改寫到正確的格子 |
| 3 | 追問「以便…」，找出真正的需求 | 把「我想要…」當成一種可能的解法，追問「以便…」，找出真正的需求。過程中發現新的利害關係人，就加進清單 |
| 4 | 使用者故事總表 | 整理成使用者故事總表，每則故事有編號（例如 O03-US02、I01-US04）。相同的需求用相同需求群組（N01、N02…）連結 |
| 5 | 依需求排序 | 依**需求**排出優先順序（所有議題都用 MoSCoW），並和利害關係人協商。每個需求有一個優先順序。不使用分數、權重或公式，因為輸入是質性資料 |
| 6 | 候選解法、成效衡量與衝突 | 以「我想要…」為起點，並參考其他城市或國家的做法，發想能滿足優先需求的解法。每個解法列出它滿足的需求，以及成效衡量方式（含現況數值與資料來源）。「我想要…」之間有衝突時，先找能滿足雙方需求的解法；找不到時，再引入審議民主的方法 |
| 7 | 評估解法 | 評估每個解法：相關法規、隱私問題、其他顧慮與風險（包含相關的災害）、可行性，以及執行計畫（負責局處、需要的資料／API／資源、成本、執行步驟） |

#1、#2、#3、#4、#5、#6、#8、#9、#10、#11、#12 都用這個依需求排序的格式。2026-10-20 以前的版本是舊格式（依故事排序），讀法見[如何閱讀議題分析](docs/method.md#舊格式)。

完成 7 個步驟後，每個議題檔案的開頭有一節「分析摘要」：整理難以取捨的決定、解法推動時可能的爭議、受影響較大的弱勢族群、法規上的障礙，以及相依事項與現行政策的關係。摘要不加入新的事實，每一項都列出它來自哪些故事、衝突或解法。

完整的方法說明（英文）：[human-inputs.md](docs/human-inputs.md)。

各議題檔案共用的閱讀方式（標記、編號、排序原則等）：[如何閱讀議題分析](docs/method.md)。

## 跨議題分析

#1、#2、#3、#4、#5、#6、#8、#9、#10 有 44 位共用的利害關係人，例如身心障礙者、高齡者、推嬰兒車的家長與工務局新建工程處。樹、清潔箱、吸菸區與公車站位也常在同一段人行道上。所以這九個議題另外做了跨議題分析：[cross-issue/cross-issue-analysis.md](cross-issue/cross-issue-analysis.md)（試作）。#11 與 #12 在 2026-10-24 加入，還沒有加入跨議題分析；要不要加入，由作者決定。

- 列出共用的利害關係人、跨議題的共同需求（X-N01…）、跨議題的衝突（X-C1…），以及合併的解法（解法 X-A…）。
- 合併的解法由各議題的解法組成，例如樹、清潔箱與吸菸區的參與式選址一起辦（解法 X-A）。它不取代各議題的解法。
- 優先順序沿用各議題的結果，不重新排序。
- #9 在 2026-10-20 依作者的決定加入。#9 評估的是分析方法與網站，不是街道設施，所以它和其他議題相同的需求不多：#9 的需求加入 X-N04 與 X-N08，#9 解法 D 加入解法 X-D（開放資料）。規則見[如何閱讀議題分析](docs/method.md#跨議題分析)。
- #3、#4、#5、#6 在 2026-10-23 依作者的決定加入，用相同的規則。新增的跨議題的共同需求是 X-N09–X-N15，新增的衝突是 X-C3（同一條道路的空間），新增的合併的解法是解法 X-F–X-K，例如老舊公寓的到府診斷（防鼠與耐震，解法 X-G），以及通勤公車與接駁的共同規劃（解法 X-H）。
- #10 在 2026-10-24 依作者的決定加入，用相同的規則。#10 的需求加入 X-N03 與 X-N13，新增的跨議題的共同需求是 X-N16（陳情之後看得見處理的結果）與 X-N17（住戶之間的糾紛有調解的管道）。#10 解法 A 加入解法 X-C（共用的通報入口），新增的合併的解法是解法 X-L（鄰近工地的通知與施工噪音）與解法 X-M（菸味與噪音糾紛的規約範本）。沒有新的跨議題衝突。

## 使用者故事總表的格式轉換

每個議題資料夾都有 `user-stories.csv`，如有需要，可以直接匯入 Google 試算表（檔案 → 匯入）。匯入後，試算表裡**看不到**本頁開頭的說明。請把下面這段文字放在**試算表標題或第一列**，讓讀者知道 `[AI模擬]` 的意思：

> 標記 [AI模擬] 的內容不是真實訪談，也不是真實市民的話；標記 [AI整理] 的內容由 AI 從真實資料整理，還沒有經過真人查核；標記 [實證] 的內容有可查證的出處，或已經由真人查核。

「優先順序」欄使用 MoSCoW（M、S、C、W），它是這則故事的需求的優先順序；「相同需求編號」欄（N01…）表示哪些故事有相同的需求。試算表依字母排序時，順序會變成 C、M、S、W，所以建議用篩選，不要用排序。

修改任何 `issue-analysis.md` 或共用的 CSV 檔之後，請在 repo 根目錄執行這個指令（需要 Python 3）：

```
analysis/scripts/build_all.sh
```

這個指令會依序執行下面的步驟。任何一步失敗就會停止。修改 `cross-issue/cross-issue-analysis.md` 之後，也請執行這個指令。

| 步驟 | 程式 | 內容 |
|---|---|---|
| 1 | `sync_stakeholders.py` | 更新 `data/stakeholders.csv` 的「議題」欄 |
| 2 | `build_csv.py` | 從每個議題的步驟 4 表格重建 `user-stories.csv` |
| 3 | `update_dates.py` | 更新 `data/updated-dates.csv`（利害關係人、解法、故事與空間類型的更新日期） |
| 4 | `check_analysis.py` | 檢查每個議題的 `issue-analysis.md` 與 `user-stories.csv` |
| 5 | `check_cross_issue.py` | 檢查跨議題分析 |
| 6 | （unittest） | 執行 `tests/` 的單元測試 |
| 7 | `build_json.py` | 產生 app 用的 JSON（預設寫到 `app/public/data`，跨議題分析是 `cross-issue.json`） |
| 8 | `build_flat.py` | 從這些 JSON 產生整理好的資料表：每一種項目一個 CSV 和一個 JSON 檔，寫到 `<輸出資料夾>/flat/`（說明見[資料說明](docs/data-guide.md)） |

可以指定輸出資料夾，例如 `analysis/scripts/build_all.sh /tmp/out`。加上 `CI=true` 時，如果步驟 1–3 重新產生的檔案和最後一次提交不同，指令會失敗（GitHub Actions 用這個模式）。

檢查會確認編號（包含 `#2 O01-US01` 這種跨議題引用）、連結、標記、優先順序與 CSV 是否一致。指令更新了 CSV 時會提醒你，請一起提交。

## 資料使用說明

- 「市長，你給我聽好了」資料只用來整理件數和改寫的摘要（標記 `[AI整理]`），不引用原始留言，原始檔案不公開，也不辨認任何個人。依活動規則，該資料僅限於此黑客松活動使用。`[AI整理]` 的件數是 AI 用關鍵字比對算出的估計，需要真人抽查。
- 開放資料各數字的來源與計算方式，寫在每個議題檔案的附錄。
- 想再利用資料：每一種有編號的項目（議題、利害關係人、故事、需求、衝突、解法、跨議題的編號等）都有一個整理好的 CSV 和 JSON 檔案，放在網站的 `data/flat/`。欄位、編號、標記與授權的說明見[資料說明](docs/data-guide.md)。
