# 提案小幫手

在提案之前，先看見各方利害關係人的關注。

> 本作品由一位個人參加者用 AI 協助製作，與主辦單位無關，也不代表主辦單位或市府的立場。標記 `[AI模擬]` 的內容不是真實訪談，也不是真實市民的話。

- 網站：https://etblue.github.io/pumadebugthon/
- 原始碼：<https://github.com/ETBlue/pumadebugthon>
- 議題分析（本工具的資料來源）：[`analysis/`](../analysis/)

## 1. 這是什麼

市民想參與政策討論，但常常不知道其他人關心什麼。只從自己的角度出發，意見容易不完整，也不容易被採用。

這個工具把 [`analysis/`](../analysis/) 裡的議題分析，整理成可以瀏覽的網頁。市民可以先看見一個議題的所有利害關係人、他們想要什麼、彼此的衝突，以及可能的解法，再提出自己的意見。

這個工具也想幫助公務員。如果政策分析都用同一種格式，分析結果就是結構化資料。公務員可以依利害關係人或空間，查到以前相關議題的分析，再拿來使用，減少分析階段的工作。

目前有兩個議題的分析：#1 把三千棵樹種回來、#2 找回消失的垃圾桶。

## 2. 功能

| 頁面 | 內容 |
|---|---|
| 首頁 | 議題清單（含各種數量與空間類型），以及跨議題的利害關係人清單（組織分類樹、個人分組、「只看跨議題」與「特別關注」篩選） |
| 議題頁 | 5 個分頁：總覽（數量、標記說明、使用相同空間的議題、待補清單）、你的意見、利害關係人、衝突、解法 |
| 你的意見 | 從清單選一件你想要的事，看看：誰也想要、誰可能有不同意見、有哪些相關解法、還有誰沒有被提到 |
| 利害關係人頁 | 一位利害關係人在每個議題的故事、優先順序、相同訴求群組、衝突、涵蓋的解法、還沒有解法涵蓋的故事 |
| 空間頁 | 同一種城市空間（例如人行道）上，各議題的解法與相關的利害關係人 |

- 每個表格格子都顯示自己的標記，只截圖一部分也看得到。
- 可以只用鍵盤操作，手機寬度也能閱讀。
- 不需要登入。網站本身不收集使用者的資料。

## 3. 資料來源：哪些是真實資料、哪些是模擬資料

網站上每個格子都有標記：`[實證]`、`[AI模擬]`，或 【待補】。

| 標記 | 內容 | 來源 |
|---|---|---|
| `[實證]` | 題目原文的內容 | 市政 debug 松的題目頁 |
| `[實證]` | 開放資料的數字（見下表） | 政府開放資料，一般下載，依各資料集的授權使用（多數為政府資料開放授權條款） |
| `[AI模擬]` | 大部分的使用者故事（「我想要…」「以便…」）、與本題的關係、優先順序、相同訴求群組、衝突與審議的模擬結果、解法、成效衡量的目標 | 由 AI 推想。**不是真實訪談，也不是真實市民的話** |
| 【待補】 | 需要真人提供的資訊 | 例如局處確認數字、法務確認。每個議題的「待補清單」列出全部項目 |
| （不標記） | 利害關係人清單、分類路徑、空間類型 | 作者整理的分類，見 [`stakeholders.csv`](../analysis/stakeholders.csv)、[`path-labels.csv`](../analysis/path-labels.csv)、[`space-types.csv`](../analysis/space-types.csv) |

表格只是大致的分類，以每個格子上的標記為準。例如少數使用者故事來自題目原文，標記為 `[實證]`；首頁的「實證比例」列出每個議題有幾則。

## 5. 如果市府上任 100 天內要落地，需要做什麼

以下是作者的建議，負責局處與成本都需要市府確認。

**最重要的前提：** 目前大部分內容是 `[AI模擬]`。在市府使用或公開引用之前，必須先用真實的輸入（訪談、工作坊、陳情資料、局處資料）取代 `[AI模擬]` 的內容。

### 要做的事

| 時間 | 要做的事 | 建議負責 |
|---|---|---|
| 第 1–30 天 | 選 2–3 個真實議題試辦，例如本作品的 #1、#2。確認分析格式（利害關係人編號、分類路徑、空間類型、標記規則）。 | 研考會（政策流程）、各議題的主管局處 |
| 第 1–30 天 | 決定網站放在哪裡，例如維持 GitHub Pages 的靜態網站，或放到市府的主機。 | 資訊局（平台） |
| 第 31–70 天 | 用真實輸入取代 `[AI模擬]`：訪談利害關係人、舉辦工作坊、整理 1999 與「市長，你給我聽好了」的件數或摘要。補上【待補】項目。 | 各議題的主管局處，例如 #1 工務局公園處與新工處、#2 環保局；研考會協助 |
| 第 71–100 天 | 公開試辦議題的分析，讓市民在參與討論前先瀏覽。收集市民與公務員的回饋，修改格式。 | 研考會、資訊局 |
| 第 71–100 天 | 把共用的利害關係人清單，當成全市共用的資料來維護。 | 研考會 |

### 重複使用：減少公務員的分析工作

- 共用的利害關係人清單（例如 `I06` 身心障礙者）在每個議題都是同一個編號。這份清單可以成為全市共用的資料。
- 新議題開始時，公務員可以依利害關係人或空間（例如「人行道」），查到以前相關議題的分析：誰受影響、有哪些衝突、試過哪些解法。
- 例如：「人行道」上同時有 #1 的樹穴與 #2 的清潔箱，兩個議題都要考慮身心障礙者與推嬰兒車的家長的通行寬度。

### 需要的資料

| 資料 | 用途 | 目前狀況 |
|---|---|---|
| 「市長，你給我聽好了」的件數或摘要 | 把 `[AI模擬]` 換成 `[實證]` | 尚未釋出 |
| 1999 陳情的類別與件數 | 同上，並找出問題的地點與數量 | 已有開放資料，但部分類別混在一起，也沒有地點欄位 |
| 各局處的業務資料（例如清潔箱的現況清單、行道樹的移除紀錄） | 補上【待補】的數字 | 部分沒有公開，或資料較舊 |
| 訪談、工作坊、公聽會的紀錄 | 取代 `[AI模擬]` 的故事與衝突 | 需要新收集 |

### 成本（粗估）

| 項目 | 粗估 |
|---|---|
| 網站 | 靜態網站，沒有伺服器與資料庫。放在 GitHub Pages 不用費用；放在市府主機的費用【待補：資訊局估算】 |
| 分析人力 | 主要的成本。每個議題需要整理利害關係人、訪談、撰寫分析【待補：每個議題需要的人力與天數】 |
| 真實輸入的收集 | 訪談、工作坊、公聽會的場地與人力【待補：依議題規模估算】 |
| 維護共用清單 | 少量的持續人力【待補】 |

以上都是估計，不是報價。

## 6. 本機執行

需要 Node 22 與 Python 3。

```
cd app && npm ci && npm run data && npm run dev
```

- `npm run data`：從 `analysis/` 產生網站用的 JSON（寫到 `app/public/data`）。
- `npm run dev`：開發用伺服器，網址為 <http://localhost:5173/pumadebugthon/>。

測試：

```
cd app && npm test        # 網站的測試（Vitest）
analysis/build_all.sh     # 在 repo 根目錄執行：檢查議題分析並執行 Python 測試
```

建置：`cd app && npm run build`，結果在 `app/dist`。
